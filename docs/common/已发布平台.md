### 3.2 提交 + 打 tag

```sh

```

### 3.3 推送（必须走代理，否则直连 GitHub 慢/超时）

```sh

```

### 3.4 GitHub Release

```sh

  --title "vX.Y.Z — <标题>" --notes-file /tmp/release-notes.md
```

### 5.1 收录条目结构（⚠️ 无版本字段）

- `data/plugins/PolinniZhong__dsh-personal-center.yml`：`url` / `name` / `category` / `description`（en + zh）；

**迭代时不需要"更新版本号"，要更新的是描述**——新功能补进 en/zh 文案（例：v1.0.0 补「外观全局字号」/ "a global font-size adjuster"）。

### 5.2 开 PR 的流程

1. **fork 实际叫 `PolinniZhong/awesome-dsh-plugin-org`**（文档旧写 `-1` 已改名，以 `gh repo view` 为准）；
2. fork 落后上游先同步：`gh api -X POST repos/PolinniZhong/awesome-dsh-plugin-org/merge-upstream -f branch=main`；
3. 分支**基于上游 main 最新 SHA** 建（避免 fork 的 merge commit 污染 PR）：`POST .../git/refs {"ref":"refs/heads/<branch>","sha":<upstream sha>}`；
4. 改文件走 API（本地 clone 直连 GitHub 会超时）：contents GET（拿 blob sha）→ 改内容 → PUT（`message/content/sha/branch`）；
5. 开 PR：`POST /repos/awesome-dsh-plugin/awesome-dsh-plugin/pulls`，head = `PolinniZhong:<branch>`，base = `main`；
6. 上游合并后 **dsh-market 自动同步**（数据源 = awesome-dsh-plugin），无需额外操作。

## 十二、踩坑记录

| 坑 | 现象 | 对策 |
|---|---|---|
| npm 2FA | 静态 token / `--otp` → 403 | 交互式 `npm publish`，用户现场输 OTP |
| 直连 GitHub 慢/超时 | clone/fetch 60s 超时 | git 命令加代理 7897；远程 API 操作走 `gh api` |
| fork 改名 | 文档写 `awesome-dsh-plugin-1` | 实际 `PolinniZhong/awesome-dsh-plugin-org`，以 `gh repo view` 为准 |
| fork 落后上游 | 基于上游 SHA 建分支报错 | 先 `merge-upstream` 同步 fork main（会推送到 fork main），再基于上游 main SHA 建分支 |
| **fork 站点构建失败** | merge-upstream 推送到 fork main 触发上游继承的 build-site 工作流，对 2777 个仓库探测 stars/readmes/updates，**耗尽 GitHub API 配额**，构建必挂（日志明示 "not a data problem"） | **fork 只是 PR 来源，保持其 Actions 禁用**（`gh api -X PUT repos/PolinniZhong/awesome-dsh-plugin-org/actions/permissions -F enabled=false`）；PR 检查在上游仓库跑，不受影响 |
| 展示帖编号 | 交接文档写 #3449 | 当前帖是 #3595（#3449 已过时），以本文件为准 |
| 收录条目无版本 | 想"升版本号" | 目录不展示版本，只需同步描述文案 |
| 会话并行编辑 | 一个 `lib/client.js` 混两个会话改动 | 按用户拍板合并同一 commit，不强行拆 |
